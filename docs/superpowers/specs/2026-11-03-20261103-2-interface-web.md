# herness — interface web : design

Date : 2026-11-03 · Auteur : Maxime Vozelle (avec Claude) · Mission 20261103-2

## Intention

Piloter herness demande aujourd'hui de regarder herdr : le cockpit et le panneau
`tasks` (TUI au clavier), la conversation avec l'orchestrateur (Claude Code dans
un panneau), les visionneuses `spec` / `plan`, les onglets `agents` et `checks`.
L'utilisateur veut **quelque chose de plus ergonomique : cliquer sur des
boutons, et ne plus avoir à regarder de terminal.**

L'**interface web** est une application locale, ouverte dans le navigateur, qui
fait **tout** ce que l'utilisateur fait aujourd'hui en regardant herdr :
suivre et piloter les missions de tous ses projets, **discuter avec
l'orchestrateur**, valider ou refuser les portes, lire la spec et le plan, voir
si les agents et les checks avancent. herdr reste ouvert et fait tourner les
missions en dessous ; l'utilisateur ne le regarde plus. *(Décision de
l'utilisateur : « herdr peut rester ouvert, je veux juste plus le regarder ».)*

## Objectifs

- Une commande `herness web` qui démarre (si besoin) un serveur local et ouvre
  l'interface dans le navigateur.
- Une page unique en **trois colonnes** *(décision de l'utilisateur, maquette A)* :
  missions | conversation | panneau contexte à onglets.
- Toutes les missions de **tous les projets configurés**, filtrables par projet.
- Tous les gestes du cockpit et du panneau `tasks` : valider / refuser une porte
  (avec ou sans note), reprendre, redémarrer, fermer, supprimer, ouvrir l'espace
  herdr, démarrer une nouvelle mission.
- La **conversation complète avec l'orchestrateur** dans la page : lire ses
  messages, lui écrire. *(Décision de l'utilisateur : « mettre tout dans le
  navigateur ».)*
- Le suivi **en lecture seule** des agents et des checks, pensé pour répondre
  d'un coup d'œil à « ça avance ou c'est bloqué ? ».
- **Temps réel** : tout changement visible en moins d'une seconde, sans
  rechargement.

## Non-objectifs

- Accès depuis un autre appareil (téléphone, autre poste) : le serveur n'écoute
  que sur `127.0.0.1`. *(Décision de l'utilisateur : « juste sur mon poste en
  localhost (pour l'instant) ».)* Donc pas de comptes ni d'authentification
  utilisateur au-delà de la protection décrite plus bas.
- Remplacer herdr ou faire tourner les missions sans herdr.
- Modifier le moteur, la machine à états ou le format de `state.json`.
- Répondre à un agent (implémenteur, relecteur) depuis la page : c'est le rôle
  de l'orchestrateur. *(Décision de l'utilisateur : « ça m'arrive jamais de
  devoir répondre moi-même ».)*
- Un terminal embarqué (recopie brute d'un panneau herdr).
- Éditer la spec ou le plan depuis la page.
- Retirer le cockpit TUI ou les commandes existantes : tout reste disponible.

## Anti-objectifs

- **Une interface lente ou pas à jour en temps réel.** *(Ce qui ferait grimacer
  l'utilisateur.)* Concrètement : une page qui met plus d'une seconde à
  refléter un changement, qui demande de recharger, qui affiche un état figé
  sans le signaler, ou qui met plusieurs secondes à s'ouvrir.
- Une page qui écrit `state.json` : le moteur reste le seul écrivain. Le serveur
  passe uniquement par les fonctions existantes (boîte de réception via
  `decide`, fonctions de cycle de vie de `src/ui/actions.ts`).
- Une décision envoyée deux fois pour la même porte (même garde que le cockpit :
  rien pendant qu'une décision part, porte décidée ignorée tant que l'état la
  montre en attente).
- Une décision, une fermeture ou une suppression sans confirmation explicite
  dans la page.
- Une interface qui permettrait à un agent de franchir une porte plus
  facilement qu'aujourd'hui (voir « Protection »).

## Ce qui a été décidé

### Lancement

- `herness web` *(mon choix pour le nom et les options)* :
  - si aucun serveur ne tourne, le démarre **détaché** (il survit à la fermeture
    du terminal) puis ouvre le navigateur sur l'interface (`xdg-open`) ;
  - si un serveur tourne déjà, ouvre seulement le navigateur ;
  - `--arreter` : arrête le serveur ;
  - `--redemarrer` : arrête puis relance (après une mise à jour de herness) ;
  - `--premier-plan` : tourne au premier plan dans le terminal courant (journal
    à l'écran), pour le débogage ;
  - `--sans-navigateur` : n'ouvre pas le navigateur, affiche l'adresse ;
  - `--port <n>` : port d'écoute, **4747 par défaut** *(mon choix)*. Port déjà
    pris par autre chose qu'un serveur herness : erreur claire.
- Le serveur écrit ses informations (pid, port, version, jeton) dans
  `~/.local/state/herness/web.json` (sous `HERNESS_HOME`), en mode `0600` ; il
  le supprime à l'arrêt. Un `web.json` dont le pid ne tourne plus est ignoré.
- Comme `herness dev`, `herness web` **exige `HERDR_ENV`** (lancé depuis un
  panneau herdr) : le serveur hérite de l'environnement herdr dont il a besoin
  pour démarrer, reprendre et parler aux agents. Hors herdr : message
  « lance herness web depuis un panneau herdr » et rien d'autre.
- Le journal du serveur va dans `~/.local/state/herness/logs/web.log`.
- Le README gagne une section « Interface web » et une ligne dans le tableau des
  commandes ; « Limites actuelles » est mise à jour.

### Protection

Le serveur n'écoute que sur `127.0.0.1`. Pour qu'un autre site ouvert dans le
navigateur ne puisse pas piloter herness :

- un **jeton** aléatoire est généré au démarrage ; `herness web` ouvre
  `http://localhost:<port>/?cle=<jeton>`, le serveur le pose dans un cookie
  `HttpOnly; SameSite=Strict` puis redirige vers `/` sans le jeton dans l'URL ;
- toute requête sans le bon cookie reçoit `401` (page « relance herness web ») ;
- toute requête qui modifie quelque chose (`POST`) doit avoir un en-tête
  `Origin` égal à `http://localhost:<port>` ou `http://127.0.0.1:<port>`, et
  l'en-tête `Host` est vérifié de même (rebinding DNS).

Le niveau de protection face à un agent local est **le même qu'aujourd'hui** :
un agent qui tourne sous le même utilisateur pourrait, en le voulant
délibérément, lire `web.json` comme il pourrait aujourd'hui simuler un terminal
pour `herness valider`. La règle « seul l'utilisateur valide » reste portée par
les prompts des agents et par la confirmation explicite dans la page. Le prompt
de l'orchestrateur (`src/prompts/orchestrator.md`) gagne la consigne de ne
jamais appeler l'interface web. *(Décision de l'utilisateur : ce niveau de
protection, équivalent à aujourd'hui, lui convient.)*

### Disposition

Trois colonnes *(décision de l'utilisateur, maquette « Vue d'ensemble »)*,
largeur fixe à gauche (~230 px) et à droite (~360 px, redimensionnable *(mon
choix)*), conversation au centre. Thème clair et sombre suivant le système.
En dessous de ~1100 px de large, le panneau de droite passe en tiroir ouvrable
*(mon choix)* ; l'interface n'a pas à être pensée pour mobile.

#### Colonne de gauche : missions

- Toutes les missions de tous les projets, avec en tête un sélecteur « Projet :
  tous ▾ » (mémorisé dans le navigateur).
- Chaque ligne : identifiant, projet, slug (ou début de la demande), statut
  court (même libellé que le cockpit, `statusLabel`). Bordure ambre : porte en
  attente ; rouge : bloquée ; normale : active ; grisée : terminée.
- Tri identique au cockpit (`sortMissions`) ; la sélection reste sur la même
  mission si l'ordre change.
- Masquage des missions terminées identique au cockpit (`isHidden`, état des PR
  via `PrCache`), avec la ligne « N missions terminées masquées · afficher ».
- **Badge « attend ta réponse »** *(décision de l'utilisateur)* sur toute
  mission active, sélectionnée ou non, dont l'orchestrateur a fini de parler
  et attend l'utilisateur : son agent herdr n'est pas `working` et la dernière
  entrée utile du transcript est un message texte de l'orchestrateur, postérieur
  au dernier message de l'utilisateur et au dernier message `[herness]`. Badge
  **« attend dans herdr »** quand l'orchestrateur est `blocked` (demande de
  permission, menu…). Une mission avec badge remonte avec les missions qui
  attendent une décision (même compartiment que les portes en attente)
  *(mon choix)*.
- **Notifications du navigateur** *(décision de l'utilisateur)* : la page
  demande la permission une fois (bouton dans l'en-tête de la colonne, pas de
  demande au chargement). Une notification part quand, sur n'importe quelle
  mission : une porte s'ouvre, l'orchestrateur se met à attendre une réponse ou
  attend dans herdr, la mission devient bloquée *(ce dernier cas : mon choix)*.
  Pas de notification si la page est visible et que cette mission est
  sélectionnée. Un clic sur la notification ramène la page et sélectionne la
  mission. Une seule notification par événement, même avec plusieurs onglets
  ouverts *(mon choix)*.
- Bouton « + Nouvelle mission » en bas : formulaire projet (liste des projets
  configurés, présélectionné sur le filtre courant) / demande (lien Wrike,
  issue GitHub ou texte, plusieurs lignes) / note facultative. « Démarrer »
  appelle `startMission` avec le `repoPath` du projet comme `cwd`. La sortie de
  la commande (lignes `KO`, erreur) s'affiche dans le formulaire en cas
  d'échec ; en cas de succès la nouvelle mission est sélectionnée.
- L'URL reflète la mission sélectionnée (`/#/<id>`) pour qu'un rechargement ou
  un favori y ramène *(mon choix)*.

#### Colonne centrale : en-tête et conversation

- **En-tête** de la mission : identifiant · slug, projet, branche, étape,
  `EN PAUSE`, motif de blocage (`blockedReason`) en rouge, lien vers la PR.
  Boutons : « Ouvrir dans herdr » (`open` : active l'espace de la mission dans
  herdr ; herness ne peut pas ramener la fenêtre du terminal au premier plan,
  surtout sous Wayland, donc la page affiche « espace ouvert dans herdr —
  bascule sur ta fenêtre herdr » *(mon choix)*), « Reprendre » (`resume`, désactivé
  sur une mission terminée), « Redémarrer » (`restartDetached`), menu « ⋯ » :
  « Fermer » (confirmation, et seconde confirmation s'il reste du travail, comme
  le cockpit), « Supprimer » (missions fermées seulement, confirmation). Les
  boutons inutilisables sont grisés avec une infobulle qui dit pourquoi. Pendant
  une action, le bouton montre qu'elle est en cours ; son résultat s'affiche
  dans un bandeau (succès 5 s, erreur jusqu'à fermeture, 8 lignes au plus,
  comme le cockpit).
- **Conversation** avec l'orchestrateur, en bulles :
  - messages de l'utilisateur à droite, réponses de l'orchestrateur à gauche
    (Markdown rendu) ;
  - messages du moteur (`[herness] …`) en ligne discrète bordée d'ambre ;
  - **mode discret** *(décision de l'utilisateur, maquette A)* : les actions de
    l'orchestrateur entre deux messages (outils : lecture de fichier, commande,
    outils herness…) sont regroupées en une ligne « ▸ N actions — résumé ».
    Un clic déplie la liste ; un clic sur une action montre son détail
    (paramètres et résultat, tronqués avec « voir tout »). *(L'utilisateur :
    « je peux appuyer sur ce qu'il faut pour voir plus les détails ».)*
  - la réflexion interne du modèle (blocs `thinking`) n'est pas affichée ;
  - les éléments techniques du transcript (méta, rappels système, instantanés,
    titres…) ne sont pas affichés ;
  - indicateur « ● l'orchestrateur travaille… » quand il est occupé ;
  - bandeau ambre « l'orchestrateur attend une intervention dans herdr » +
    « Ouvrir dans herdr » quand herdr le dit bloqué ;
  - zone de saisie en bas : Entrée envoie, Maj+Entrée passe à la ligne. Le
    message s'affiche aussitôt (en attente) puis devient normal quand il
    apparaît dans le transcript. Envoyer pendant que l'orchestrateur travaille
    est permis (Claude Code met le message en file).
  - défilement : la vue suit le bas tant que l'utilisateur n'est pas remonté ;
    sinon un bouton « nouveaux messages ↓ » apparaît.
- **Portes en attente** : chaque porte en attente de la mission apparaît comme
  une carte épinglée en bas de la conversation (au-dessus de la saisie) : type,
  résumé, fichier concerné (lien vers l'onglet Spec ou Plan), boutons
  « Valider », « Refuser », « Avec une note… ». « Valider » ouvre une
  confirmation « Valider <porte> (<type>) de <mission> ? » ; « Refuser » et
  « Avec une note… » ouvrent une saisie de note (obligatoire pour refuser) puis
  la même confirmation. Plusieurs portes : plusieurs cartes, la plus ancienne en
  premier. Une porte décidée disparaît quand l'état la montre décidée.

#### Colonne de droite : onglets

Onglets : **Tâches · Spec · Plan · Agents · Checks · Journal**. Un point sur
l'onglet signale du nouveau (amendement en attente sur Spec ou Plan, agent qui
attend une intervention, check rouge).

- **Tâches** : la liste des tâches du plan (numéro, titre, phase, tour/3),
  pastille verte (faite), bleue (en cours), grise (à faire), rouge (en échec /
  bloquante). Un clic sur une tâche déplie ses fichiers présents dans
  `taches/<n>/` du dossier de mission (brief, rapport, revue, re-revues,
  correctifs, diffs), chacun ouvrable dans le panneau (Markdown rendu, diff
  coloré). Sous la liste : revue globale (tour), preflight (tour, résultats
  ✓/✗ et durée), et les mêmes fichiers pour `global/` et `preflight/`.
- **Spec** et **Plan** : le document rendu en Markdown, rechargé dès qu'il
  change. Même priorité que `herness voir` : une proposition en attente
  (`spec.proposed.md` / `plan.proposed.md`) l'emporte, signalée par un en-tête
  « Proposition d'amendement en attente » avec une bascule « Proposition /
  Différences avec la version actuelle » (diff par lignes) ; sinon le fichier
  du worktree ; sinon « pas encore écrit ». Mission fermée (worktree supprimé) :
  l'onglet Plan affiche `plan.approved.md` du dossier de mission s'il existe,
  l'onglet Spec affiche « worktree supprimé : spec plus disponible ici »
  *(mon choix)*.
- **Agents** *(décision de l'utilisateur : lecture seule)* : une carte par agent
  connu de l'état de la mission (implémenteurs et relecteurs de chaque tâche,
  revue globale, correcteurs, diagnostic, preflight), la plus récente en haut :
  rôle, tâche, outil (Claude / Cursor), tour, état herdr (`working`, `idle`,
  `done`, `blocked`), **« dernière activité il y a N s »** (dernier changement
  de sa sortie), ses ~5 dernières lignes de sortie, bouton « Voir toute la
  sortie » (les ~400 dernières lignes, rafraîchies en direct). Carte ambre si
  l'agent est `blocked` ou fait l'objet d'une porte `agent-bloque`. Les agents
  terminés sont repliés. Pas de bouton pour répondre.
- **Checks** : les tests de tâche et le preflight, du plus récent au plus
  ancien, d'après les fichiers de `logs/` de la mission (`<horodatage>-<slug>.log`,
  `.exit`) : nom, en cours / vert / rouge, durée, **« dernière sortie il y a
  N s »** pour un check en cours, les premières lignes d'erreur pour un rouge,
  « Voir tout le journal ». Le preflight est présenté étape par étape d'après
  `loops.preflight.results` (étapes pas encore lancées en gris).
- **Journal** : tout `state.log`, le plus récent en haut.

### Conversation : comment ça marche

- **Lecture** : herness fixe lui-même l'identifiant de session de
  l'orchestrateur (`state.orchestrator.sessionId`). Claude Code écrit le
  transcript dans `~/.claude/projects/<dossier encodé>/<sessionId>.jsonl`. Le
  serveur le trouve en cherchant `<sessionId>.jsonl` dans les sous-dossiers de
  `~/.claude/projects/` (plutôt que de recalculer l'encodage du chemin), le lit
  **en continu à partir du dernier octet lu** (pas de relecture complète à
  chaque changement : un transcript fait couramment plusieurs centaines de Ko)
  et pousse les nouvelles entrées à la page.
- **Envoi** : `herdr agent prompt <o<id>> <texte>` sans attente
  (`Herdr.agentPrompt(…, { wait: false })`), comme le moteur pour ses messages
  `[herness]`. Si l'agent orchestrateur n'existe pas dans herdr (`agentGet`
  rend `null`), la saisie est désactivée avec « orchestrateur arrêté —
  Reprendre ».
- **Occupé / bloqué** : `agentGet(o<id>).state` (`working`, `blocked`…).
- **Questions à choix** *(décision de l'utilisateur : texte libre)* :
  l'orchestrateur pose ses questions en texte libre. L'outil de question à choix
  de Claude Code (`AskUserQuestion`), qu'on ne peut pas remplir depuis la page
  de façon fiable, est **interdit** : ajouté aux `--disallowedTools` de
  l'orchestrateur dans `agentArgs` (`src/agents/adapters.ts`) — ce qui
  s'applique aussi aux missions en cours dès que leur orchestrateur est relancé
  (`--resume` repasse les mêmes arguments) — et le prompt de l'orchestrateur
  dit de poser les questions en texte. Si une telle question apparaît quand même
  en attente dans le transcript (ancienne session), la page l'affiche avec ses
  options, en lecture seule, et le bouton « Répondre dans herdr ».
- Le prompt de l'orchestrateur (`orchestrator.md` du dossier de mission) est
  écrit à la création de la mission : les missions déjà en cours ne reçoivent
  pas les nouvelles consignes du prompt ; c'est accepté *(mon choix)*.
- Le format du transcript n'est pas une API publique de Claude Code : toute la
  lecture est isolée dans un seul module avec des tests sur des extraits réels ;
  une entrée inconnue est ignorée sans casser l'affichage.

### Temps réel

- Un flux **Server-Sent Events** par page (`/api/evenements`), reconnexion
  automatique du navigateur. Bandeau discret « connexion perdue, reconnexion… »
  si le flux est coupé plus de 2 s ; à la reconnexion la page recharge l'état
  complet. *(Mon choix.)*
- Le serveur surveille les fichiers (`fs.watch`) : dossier des missions
  (`state.json` de chaque mission, propositions, `taches/`, `global/`,
  `preflight/`, `logs/`), spec et plan dans les worktrees, transcripts. Pour
  ne rien rater si un événement de surveillance se perd, un contrôle de date de
  modification passe en plus toutes les secondes sur les fichiers suivis
  *(mon choix)*.
- Ce qui ne s'observe pas par fichier (état et sortie des agents dans herdr)
  est **interrogé toutes les secondes** : l'état de l'orchestrateur de **chaque
  mission active** (pour les badges et les notifications), tant qu'au moins
  une page est connectée *(mon choix)* ; l'état et la sortie des autres agents seulement pour la mission
  sélectionnée dont l'onglet Agents est ouvert. Les transcripts de tous les
  orchestrateurs actifs sont suivis par fichier.
- Objectifs mesurables : changement visible dans la page **en moins d'une
  seconde** ; première page affichée en moins d'une seconde avec une dizaine de
  missions.

### Choix techniques *(mes choix, à la demande de l'utilisateur)*

- **Serveur** : Node 24 + TypeScript, dans le dépôt herness, sous `src/web/`,
  sans framework web (`node:http`). Il réutilise directement les fonctions
  existantes : `src/ui/model.ts` (tri, libellés, masquage), `src/ui/actions.ts`
  (toutes les actions, avec `isTTY: true` et la confirmation déjà faite côté
  page, comme le cockpit), `PrCache`, `missionsRoot`/`missionDir`/`specPath`/
  `planPath`, le client herdr. Petits ajouts permis hors `src/web/` : exporter
  la liste de **tous** les projets configurés depuis `src/config/project.ts` et
  la liste de toutes les missions ; consignes ajoutées au prompt de
  l'orchestrateur ; `AskUserQuestion` ajouté aux outils interdits de
  l'orchestrateur (`src/agents/adapters.ts`) ; commande `web` dans `src/cli.ts`.
- **Config de projet modifiée** : le serveur tourne longtemps et `import()` ne
  recharge jamais un module déjà chargé. Le chargement des configs
  (`src/config/project.ts`) importe donc chaque `config.ts` avec un suffixe de
  version tiré de sa date de modification (`?v=<mtime>`), pour qu'une config
  modifiée soit relue sans redémarrer le serveur *(mon choix)*.
- **Page** : React 19 (déjà dans le dépôt), TypeScript, CSS simple avec
  variables (thème clair / sombre), **sans bibliothèque de composants**. La page
  est empaquetée par **esbuild** (nouvelle dépendance) au démarrage du serveur,
  en mémoire : aucune étape de build manuelle, l'installation reste
  `pnpm install` + lien symbolique.
- **Markdown** : `markdown-it` avec le HTML brut désactivé (le contenu affiché
  vient d'agents et de tickets : pas d'injection de HTML). **Diff** : paquet
  `diff`.
- **API** : JSON sous `/api/…` (état des missions, contenu d'un fichier de
  mission, actions), plus le flux SSE. Le serveur ne sert que des fichiers des
  dossiers de mission, des worktrees des missions (spec / plan) et des
  transcripts des orchestrateurs : aucun chemin arbitraire.
- **Tests** : vitest comme le reste du dépôt. La logique (lecture du
  transcript, regroupement des actions, modèle d'affichage, routes du serveur
  avec un faux herdr) est testée en Node ; les composants React avec
  `@testing-library/react` + `jsdom` (nouvelles dépendances de dev). Doublures
  existantes réutilisées (`test/herdr/fake.ts`, `test/fakes.ts`,
  `HERNESS_HOME` temporaire).

## Laissé au constructeur

- Le découpage du code sous `src/web/` et les noms internes.
- Le détail visuel (couleurs exactes, espacements, icônes) dans l'esprit des
  maquettes : sobre, lisible, couleurs de statut identiques au cockpit
  (ambre = décision, rouge = bloquée, gris = terminée).
- Le contenu exact du résumé « ▸ N actions — … » et du détail d'une action par
  outil, tant qu'il reste court et compréhensible.
- La forme exacte des routes de l'API et des messages SSE.
