# Interface web herness — plan d'implémentation

> **Pour les agents :** chaque tâche se fait en TDD (test d'abord, rouge, code minimal, vert), puis un commit. Les étapes utilisent des cases à cocher (`- [ ]`).

**But :** une commande `herness web` qui sert, en local, une page en trois colonnes (missions | conversation avec l'orchestrateur | onglets Tâches, Spec, Plan, Agents, Checks, Journal) qui fait tout ce que l'utilisateur fait aujourd'hui en regardant herdr, à jour en moins d'une seconde.

**Architecture :** un serveur `node:http` (`src/web/`) lit les dossiers de mission, les worktrees et les transcripts Claude Code, interroge herdr (état et sortie des agents), et pousse les changements à la page par Server-Sent Events. Les actions passent par les fonctions existantes de `src/ui/actions.ts` ; le moteur n'est pas modifié. La page (`src/web/client/`) est une application React 19 empaquetée par esbuild en mémoire au démarrage du serveur.

**Pile :** Node 24, TypeScript (exécuté par tsx), `node:http`, SSE, React 19 + `react-dom`, esbuild, `markdown-it`, `diff`, vitest, `@testing-library/react` + `jsdom`.

**Spec :** `docs/superpowers/specs/2026-11-03-20261103-2-interface-web.md` (à lire : chaque tâche l'applique).

## Contraintes globales

- Le serveur n'écoute que sur `127.0.0.1` ; port par défaut **4747** ; option `--port <n>`.
- Jeton aléatoire (32 octets en hexadécimal) ; cookie `herness_web=<jeton>; HttpOnly; SameSite=Strict; Path=/` ; sans cookie valide : `401`. Tout `POST` exige `Origin` ∈ {`http://localhost:<port>`, `http://127.0.0.1:<port>`} ; toute requête exige `Host` ∈ {`localhost:<port>`, `127.0.0.1:<port>`}, sinon `403`.
- Informations du serveur dans `<HERNESS_HOME>/web.json` (défaut `~/.local/state/herness/web.json`), mode `0600`, supprimé à l'arrêt ; journal dans `<HERNESS_HOME>/logs/web.log`.
- Le serveur n'écrit **jamais** `state.json` : décisions par `validate`/`refuse` (boîte de réception), cycle de vie par `src/ui/actions.ts`.
- Temps réel : tout changement visible dans la page en **moins d'une seconde** ; contrôle de secours des dates de modification toutes les **1000 ms** ; état herdr interrogé toutes les **1000 ms**, seulement tant qu'au moins une page est connectée.
- Couleurs de statut identiques au cockpit : ambre = décision / attend, rouge = bloquée, gris = terminée ; thème clair et sombre suivant `prefers-color-scheme`.
- Messages d'action : succès affiché 5 s ; erreur jusqu'à fermeture ; 8 lignes au plus.
- Markdown rendu avec `markdown-it` **HTML brut désactivé** (`html: false`).
- Textes de l'interface en français.
- Commits au format `feat: <description>` (ou `fix:`, `test:`, `docs:`, `chore:`).
- Après chaque commit, `git status --porcelain` doit être vide : aucun fichier non suivi ni modifié laissé dans l'arbre.
- Pas de nouvelle dépendance au-delà de : `esbuild`, `markdown-it`, `diff`, `react-dom` (dépendances) ; `@types/markdown-it`, `@types/react-dom`, `@testing-library/react`, `jsdom` (dev).
- Tests de composants React : fichier `test/web/client/*.test.tsx` commençant par `// @vitest-environment jsdom`.

## Points de vigilance pour la revue

1. **Transcript en cours d'écriture** : la dernière ligne du `.jsonl` peut être incomplète ; elle ne doit ni casser la lecture ni être perdue (relue au tour suivant). Test dans la tâche 2.
2. **Double décision** : double clic sur « Valider », ou deux onglets ouverts, ne doivent envoyer qu'une décision pour une porte ; le serveur répond `409` à la seconde. Test dans la tâche 5.
3. **Chemin hors du dossier de mission** : `chemin=../../…` ou absolu sur la route de lecture de fichier doit être refusé (`400`), jamais servi. Test dans la tâche 6.
4. **`state.json` illisible ou dossier étranger** dans le dossier des missions : ignoré sans casser la liste ni le flux ; la dernière version lisible d'une mission reste affichée. Test dans la tâche 4.
5. **Serveur redémarré pendant qu'une page est ouverte** : la page signale « connexion perdue, reconnexion… » après 2 s, se reconnecte toute seule et recharge l'état complet. Test dans la tâche 8.
