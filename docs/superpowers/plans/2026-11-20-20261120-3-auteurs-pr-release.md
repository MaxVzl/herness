# Auteurs dans la PR de release : plan d'implémentation

> **Pour les agents :** chaque tâche se fait en TDD (test d'abord, rouge, code minimal, vert), puis un commit.

**But :** afficher `by @auteur` au bout de chaque entrée de la description de la PR de release (mise à jour à chaque push sur `main`), comme dans les notes de release, et trouver l'auteur par le commit quand l'entrée n'a pas de `[#N]` exploitable.

**Architecture :** un script POSIX `.github/scripts/auteurs-notes.sh` lit des notes sur l'entrée standard et les renvoie annotées (sans doublon, jamais en erreur). `.github/workflows/release-please.yml` l'appelle pour la release créée et, à chaque passage, pour la PR de release ouverte (label `autorelease: pending`).

**Technologies :** sh/bash, `gh`, GitHub Actions, vitest + execa pour les tests (comme `test/install/install.test.ts`).

**Spec :** `docs/superpowers/specs/2026-11-20-20261120-3-auteurs-pr-release.md`

## Contraintes globales

- Appels à `gh` du script, exactement sous cette forme (le faux `gh` des tests s'y fie) :
  - `gh pr view <N> --repo <dépôt> --json author --jq .author.login`
  - `gh api repos/<dépôt>/commits/<sha>/pulls --jq '.[0].user.login // empty'`
- Annotation ajoutée : ` by @<login>` (une espace avant `by`), en fin de ligne.
- Un auteur vide, contenant `bot` ou commençant par `app/` n'annote pas la ligne.
- Une ligne qui se termine déjà par ` by @<login>` (login : `[A-Za-z0-9-]+`) reste inchangée et ne déclenche aucun appel à `gh`.
- Un échec de `gh` vaut un auteur vide : le script sort toujours avec le code 0.
- Toute ligne non annotée est recopiée octet pour octet (espaces de tête, barres obliques inverses, lignes vides comprises).
- Pas de réécriture des releases déjà publiées, pas de changement de `CHANGELOG.md` ni de `release-please-config.json`.
- Commentaires et libellés en français, comme le reste du dépôt. Les tests ne lancent jamais le vrai `gh`.

## Points d'attention pour la revue

- Dernière ligne sans retour à la ligne final : elle doit être traitée et recopiée, pas perdue (la boucle actuelle du workflow la perd). Test en tâche 1.
- `[#N]` qui désigne une issue et pas une PR (`gh pr view` échoue) : repli sur le commit de la ligne. Test en tâche 1.
- Ligne avec plusieurs `[#N]` (ex. `([#27](…)) ([#28](…))`) : seul le premier compte. Test en tâche 1.
- Ligne déjà annotée par un passage précédent (la PR est retraitée à chaque push, et ses notes deviennent celles de la release) : aucun doublon. Test en tâche 1.
- Aucune PR de release ouverte (juste après une release) : l'étape du workflow se termine sans erreur. Vérifié par lecture en tâche 2.

### Tâche 1 : Script `.github/scripts/auteurs-notes.sh`

**Test :** `pnpm vitest run test/ci/auteurs-notes.test.ts`

**Fichiers :**
- Créer : `.github/scripts/auteurs-notes.sh` (exécutable : `chmod +x`, bit `x` commité)
- Créer : `test/ci/auteurs-notes.test.ts`

**Interface produite (utilisée par la tâche 2) :** `.github/scripts/auteurs-notes.sh <propriétaire/dépôt>`. Notes sur l'entrée standard, notes annotées sur la sortie standard, code de sortie 0.

**Comportement, ligne par ligne :**
1. Si la ligne se termine par ` by @<login>` : recopiée telle quelle.
2. Sinon, si elle contient `[#N]` (le premier) : auteur = sortie de `gh pr view N …` (voir les contraintes globales).
3. Si l'auteur est vide et que la ligne contient `/commit/<40 caractères hexadécimaux>` (le premier) : auteur = sortie de `gh api repos/<dépôt>/commits/<sha>/pulls …`.
4. Si l'auteur est vide, contient `bot` ou commence par `app/` : ligne recopiée. Sinon : ligne suivie de ` by @<auteur>`.

En tête du script, un commentaire de deux ou trois lignes dit à quoi il sert, et que release-please ne nomme personne. Le style est celui du bloc actuel du workflow : boucle `while IFS= read -r line || [ -n "$line" ]`, `grep -oE`, `printf '%s\n'`, `2>/dev/null || true` sur les appels à `gh`.

- [ ] **Étape 1 : écrire les tests**

`test/ci/auteurs-notes.test.ts`. Pour chaque test, un dossier temporaire (`mkdtemp`) contient un faux `gh` exécutable placé en tête du `PATH`. Ce faux `gh` :
- ajoute ses arguments (`"$*"`) à un fichier journal ;
- répond selon ses arguments, d'après une table fournie par le test (par exemple un fichier `args<TAB>réponse` lu par le faux `gh`) ;
- sort en code 1 sans rien écrire pour des arguments absents de la table.

Le faux `gh` n'évalue pas `--jq` : la table donne directement la valeur finale. Le script est lancé avec `execa('sh', [SCRIPT, 'MaxVzl/herness'], { input, reject: false, env: { PATH: … } })`. Dépôt utilisé : `MaxVzl/herness`. Shas : 40 caractères hexadécimaux, par exemple `745ceb2b84b78eb8d9ced3e13f7fa3ed137be0b0`.

Tests (noms en français) et assertions :
- `auteur trouvé par le numéro de PR` : `* feat: x ([#14](https://github.com/MaxVzl/herness/issues/14)) ([e7bb10b](https://github.com/MaxVzl/herness/commit/<sha>))`, avec `pr view 14 --repo MaxVzl/herness --json author --jq .author.login` → `alice`. La sortie est la ligne + ` by @alice`, et le journal ne contient aucun appel `api`.
- `auteur trouvé par le commit quand la ligne n'a pas de numéro` : `* **x:** y ([745ceb2](https://github.com/MaxVzl/herness/commit/745ceb2b84b78eb8d9ced3e13f7fa3ed137be0b0))`, avec `api repos/MaxVzl/herness/commits/745ceb2b84b78eb8d9ced3e13f7fa3ed137be0b0/pulls --jq .[0].user.login // empty` → `bob`. La sortie est la ligne + ` by @bob`. La clé de la table doit correspondre à ce que `"$*"` produit réellement : à ajuster si besoin, mais l'appel du script reste celui des contraintes globales.
- `repli sur le commit quand le numéro ne donne pas d'auteur` : `[#9]` absent de la table (le faux `gh` échoue), commit → `carol`. La sortie se termine par ` by @carol`.
- `seul le premier numéro compte` : ligne avec `[#27]` puis `[#28]`, table `27` → `dave`, `28` → `erin`. La sortie se termine par ` by @dave`, sans `erin`.
- `ligne déjà annotée laissée telle quelle` : ligne de la 1re assertion terminée par ` by @alice`. La sortie est identique à l'entrée et le journal est vide.
- `bots ignorés` : `pr view` → `app/github-actions` sur une ligne, commit → `github-actions[bot]` sur une autre. Les deux lignes sont inchangées.
- `gh en échec : ligne inchangée et code 0` : aucune entrée dans la table, ligne avec `[#5]` et un commit. La sortie est égale à l'entrée et le code de sortie vaut 0.
- `texte autour recopié à l'identique` : une entrée façon PR de release de bout en bout, avec `:robot: I have created a release *beep* *boop*`, `---`, des lignes vides, `## [0.8.0](https://github.com/MaxVzl/herness/compare/v0.7.0...v0.8.0) (2026-11-20)`, `### Features`, une entrée annotable, une ligne `  indentée \ avec barre`, et le pied `This PR was generated with [Release Please](https://github.com/googleapis/release-please). See [documentation](https://github.com/googleapis/release-please#release-please).`. Toutes les lignes sauf l'entrée sont identiques. Le journal ne contient qu'un appel.
- `dernière ligne sans retour à la ligne final traitée` : entrée `"* a ([#14](…))"` sans `\n` final, avec `14` → `alice`. La sortie contient ` by @alice`.
- `script exécutable` : `(await stat(SCRIPT)).mode & 0o111` est non nul.

### Tâche 2 : Le workflow annote la PR de release et la release avec le script

**Test :** `pnpm vitest run test/ci/release-workflow.test.ts`

**Fichiers :**
- Modifier : `.github/workflows/release-please.yml`
- Créer : `test/ci/release-workflow.test.ts`

**Interface consommée :** `.github/scripts/auteurs-notes.sh <propriétaire/dépôt>` de la tâche 1 (notes sur l'entrée standard, notes annotées sur la sortie standard, code 0).

**Changements attendus dans `release-please.yml` :**
- L'étape `- uses: actions/checkout@v4` perd sa ligne `if:` : elle tourne à chaque passage, puisque le script vit dans le dépôt. Le commentaire « Archive installée par install.sh… » reste au-dessus de l'étape « Archive de la version », ou au-dessus du checkout, selon ce qui se lit le mieux.
- L'étape « Auteurs des PR dans les notes de release » garde son `if:` et son `env:`. Son `run:` devient :
  ```sh
  gh release view "$TAG" --repo "$GITHUB_REPOSITORY" --json body --jq .body > notes.md
  .github/scripts/auteurs-notes.sh "$GITHUB_REPOSITORY" < notes.md > notes-auteurs.md
  gh release edit "$TAG" --repo "$GITHUB_REPOSITORY" --notes-file notes-auteurs.md
  ```
  Le commentaire au-dessus est mis à jour : l'auteur est trouvé par la PR ou, à défaut, par le commit. Les lignes déjà annotées, venues de la PR de release, ne bougent pas.
- Nouvelle étape en dernier, sans `if:`, `name: Auteurs des PR dans la PR de release`, `env: GH_TOKEN: ${{ github.token }}`. Un commentaire au-dessus dit que release-please réécrit la description à chaque push, d'où une annotation à chaque passage. Son `run:` :
  ```sh
  pr=$(gh pr list --repo "$GITHUB_REPOSITORY" --state open --label 'autorelease: pending' --json number --jq '.[0].number // empty')
  [ -n "$pr" ] || exit 0
  gh pr view "$pr" --repo "$GITHUB_REPOSITORY" --json body --jq .body > corps.md
  .github/scripts/auteurs-notes.sh "$GITHUB_REPOSITORY" < corps.md > corps-auteurs.md
  cmp -s corps.md corps-auteurs.md || gh pr edit "$pr" --repo "$GITHUB_REPOSITORY" --body-file corps-auteurs.md
  ```
- `permissions:` inchangé.
