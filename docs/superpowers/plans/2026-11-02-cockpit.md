# herness — cockpit : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un cockpit TUI (`herness` / `herness cockpit`) dans un onglet dédié de l'espace herdr du projet, qui liste les missions du projet et permet au clavier de valider/refuser (avec note), reprendre, redémarrer, fermer, ouvrir une mission et en démarrer une nouvelle ; le panneau `tasks` de chaque mission devient la même interface limitée à sa mission.

**Architecture:** Une couche « actions » (fonctions async sans interface) enveloppe les fonctions existantes (`decide`, `resumeMission`, `closeMission`, `startMission`) et capture leurs sorties en messages ; un modèle pur classe, trie et filtre les missions ; des composants ink partagés (détail de mission, confirmation, saisie de note) servent au cockpit et au panneau `tasks`. Rien n'écrit `state.json` en dehors des fonctions existantes.

**Tech Stack:** TypeScript (ESM, strict), Node 24, ink + react, vitest + ink-testing-library, zod.

**Spec:** `docs/superpowers/specs/2026-11-02-cockpit-design.md`

## Global Constraints

- Le moteur reste le seul écrivain de `state.json` ; le cockpit n'écrit que ses propres fichiers sous `~/.local/state/herness/` (`cockpit.json`, `pr-cache.json`) et passe par l'inbox et les fonctions de cycle de vie.
- `v` et `r` n'envoient rien directement : ils affichent « Valider gN (kind) de <id court> ? Entrée / Échap » (« Refuser … ») ; seule Entrée envoie. Même règle dans le panneau `tasks`.
- Garde anti-doublon par (mission, porte) : rien n'est envoyé pendant qu'une décision part ; une porte décidée depuis cette interface est ignorée jusqu'à ce que l'état la montre non `pending`.
- `r` exige une note non vide.
- Fermer demande toujours une confirmation dans l'interface (en plus de celles de `closeMission`).
- Missions du projet : `state.repoPath === cfg.repoPath`.
- Missions terminées : `pr-ouverte` masquée quand la PR est mergée ; `fermée` sans PR masquée 7 jours après la fermeture ; `a` montre tout ; vérification des PR au plus toutes les 5 minutes.
- Mission avec une porte en attente (même bloquée) : classée « décision » (ambre). Ordre de la liste : décision, bloquée, active, terminée.
- Textes de l'interface en français. Dépôt public : aucune référence à une entreprise ou un projet réels.
- Pas de nouvelle dépendance d'exécution.

## Review Focus

1. **Touche tapée par erreur** pendant la navigation : aucune décision sans Entrée sur l'écran de confirmation → tests Tâche 6 et 7.
2. **Fonction de cycle de vie qui échoue** (contrôle KO au démarrage, moteur qui ne s'arrête pas, base non supprimée) : message d'erreur affiché, interface toujours utilisable → test Tâche 3.
3. **`$EDITOR` absent ou qui échoue** : la note en cours n'est pas perdue → test Tâche 5.
4. **`gh` absent ou hors connexion** : les missions avec PR restent affichées, aucune erreur bloquante → test Tâche 2.
5. **Onglet cockpit enregistré qui a disparu** : « retour au cockpit » le recrée au lieu d'échouer → test Tâche 4.
