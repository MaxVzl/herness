# Passage de herness en anglais : plan d'implémentation

> **Pour les agents :** chaque tâche s'exécute en TDD (test d'abord, rouge, code minimal, vert), puis un commit. Les étapes utilisent des cases à cocher (`- [ ]`).

**Objectif :** herness entièrement en anglais (CLI, MCP, état, fichiers, messages, TUI, prompts, commentaires, tests, docs), avec un réglage `language` par projet pour les documents versionnés et une migration à la lecture des anciennes missions.

**Architecture :** d'abord les renommages structurels, qui changent le contrat (valeurs d'état, commandes, garde des missions héritées, noms de fichiers, parseur du plan, réglage `language`, outils MCP, prompts). Ensuite une passe de traduction par zone du code, qui traduit d'un même geste les chaînes, les commentaires, les identifiants français et les tests associés. Une dernière tâche ajoute un test garde qui interdit le retour du français.

**Stack :** TypeScript (node 24, `tsx`), zod, commander, ink/React, vitest, pnpm.

**Spec :** `docs/superpowers/specs/2026-11-24-20261124-3-passage-anglais.md`. Lis-la avant ta tâche : elle contient les tables de renommage complètes.

## Contraintes globales

- Tout ce que tu écris ou modifies dans le code, les tests, les prompts et les docs est en **anglais** : chaînes, commentaires, noms et descriptions de tests, identifiants. Les messages de commit aussi, au format `{type}: {description}`.
- Ne jamais modifier `CHANGELOG.md`, ni les specs et plans existants de `docs/superpowers/` (historique), ni ce plan ni la spec.
- Traduire fidèlement : une règle d'un prompt ou d'un message garde son sens à l'identique. Aucun changement de comportement hors de ce que la tâche demande.
- Les tests qui vérifient un texte sont mis à jour avec le nouveau texte, jamais affaiblis ni supprimés.
- Après ta tâche, `pnpm run typecheck` doit passer. Lance aussi `pnpm run test` en entier avant de committer, car les renommages touchent des tests d'autres dossiers.
- Valeurs exactes (spec) :
  - étapes `pr-open`, `closed`, `blocked` ;
  - portes `amendment`, `arbitration`, `pr-despite-main`, `agent-blocked`, `agent-stopped`, `resume-blocked` ;
  - statut de porte `obsolete` ;
  - commandes `approve`, `reject`, `resume`, `close`, `report`, `delete`, `project`, `update`, `status`, `show` ;
  - options `--gate`, `--restart`, `--yes` ;
  - outils MCP `status`, `mission_classified`, `request_approval`, `propose_amendment`, `request_arbitration`, `pause`, `end_pause`, `abandon`, `report_anomaly` ;
  - fichiers `request.md`, `tasks/<n>/`, `report.md`, `review.md`, `review-brief.md`, `task.diff`, `branch.diff`, `errors.log`.

## Points d'attention pour la revue

- Un `state.json` hérité qui combine `step: 'bloquée'` et `blockedFrom: 'pr-ouverte'`, avec des portes `agent-arret` au statut `caduque` : tout est traduit, et la mission s'affiche (tâche 1).
- Une mission héritée à l'étape `pr-ouverte` ou `fermée` n'est **pas** refusée : `close`, `delete`, `status` fonctionnent (tâche 3).
- `update --version 0.8.1` ne propose aucun redémarrage et cite `herness reprendre <id> --redemarrer` (tâche 3).
- Un ancien `erreurs.log` avec des en-têtes `(étape X)` est relu par `report` (tâche 4).
- Dans le cockpit avec le détail ouvert, aucune touche ne déclenche deux actions (`a`, `c`, `f`…) (tâche 9).
